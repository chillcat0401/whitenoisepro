# Explore: 历史归档 Superpowers 追溯验收

## 当前问题

现有 14 个 OpenSpec 归档均已完成 `tasks.md`，当前主线也通过完整构建和规格校验。
但审计发现只有 2 个归档保留完整且已勾选的 Superpowers 执行计划，其余 12 个存在
计划未同步、缺少计划、缺少 explore 或专项评审映射不明确等问题。

当前缺口有两种性质：

- 实现正确性：可通过当前测试、lint、构建、资产和签名产物重新验证。
- 历史过程真实性：无法通过事后操作证明当时确实观察过 RED，不能伪造或倒填。

## 目标

- 为 12 个非严格通过归档建立可机器读取的追溯验收记录。
- 每条记录区分已证实、当前重验通过、无法追溯和剩余风险。
- 新增归档前自动 gate，阻止后续变更在流程证据不完整时归档。
- 将 gate 接入 Gradle `check`，让本地和后续 CI 使用同一入口。

## 方案比较

### A. 只补文档

优点：改动小。  
缺点：未来仍会重复出现未勾选 plan、缺失评审和无验证记录的问题。

### B. 追溯清单 + 自动 gate

为历史归档增加显式 `retrospective` 记录；新变更使用 `strict` 记录。Node 工具检查
OpenSpec、Superpowers plan、review 和 acceptance record，并提供 archive 前校验命令。

优点：不伪造历史，规则可自动执行，可渐进补齐旧记录。  
缺点：历史归档需要一次性建立证据映射。

### C. 重跑全部历史 TDD 并回填计划

优点：表面上所有清单一致。  
缺点：当前失败测试无法证明历史 RED，回填会制造错误审计结论。

## 决策

采用方案 B。历史记录只陈述可证明的事实；严格模式从本 change 起执行。

## 非目标

- 不修改已有产品功能或架构。
- 不声称重新执行当前测试等价于历史 TDD。
- 不自动修改旧 Superpowers plan 的 checkbox。
- 不依赖 Git 历史，因为当前项目目录不是 Git repository。
